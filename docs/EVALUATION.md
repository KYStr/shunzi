# 校對驗收：品質、速度與費用

## 狀態與目的

本文件定義可重現的驗收程序，不是通過報告。版本 0.1.0 的自動修改政策預設為空，所有模型提案都只能顯示為候選。只有經獨立驗收合格的錯誤類型，才可在明確記錄證據後啟用自動修改。

目前首次 Gemini 連線檢查收到供應商 403「Consumer suspended」，尚未執行 dev 或 holdout 模型評測；本機私有 ledger 已保守保留 NT$0.20，不表示已確認供應商實際扣款。這是 API 帳戶阻擋，不能以 mock 測試取代並宣布品質或延遲合格。

## 語料來源與隔離

`eval/corpus.jsonl` 有 240 句人工編寫繁體中文語料：

| 集合 | 明確錯句 | 正確句 | 歧義句 | 合計 |
|---|---:|---:|---:|---:|
| dev | 20 | 14 | 6 | 40 |
| holdout | 100 | 66 | 34 | 200 |
| 合計 | 120 | 80 | 40 | 240 |

使用者只提供「再／在」常混淆這個問題類型，以及「連載憶起 → 連在一起」這個片段。完整句子和其他樣本是人工構造，**不是使用者實際輸入紀錄，也不是已代表真實錯誤分布的資料集**。

每列有 `id`、`split`、`kind`、`category`、`text`、`expected`，可附 `notes`。`expected` 是最小修改後的完整句；`correct` 和 `ambiguous` 的 `expected` 一律等於原文。類別為 `homophone`、`word-boundary`、`other`。欄位含義與格式驗證詳見 [語料說明](../eval/README.md)。

只用 dev 調整 prompt、規則與門檻。holdout 在候選方案凍結後才執行一次，不得挑出失敗句直接調整再報告同一份 holdout 達標。若看過 holdout 結果後調整實作，將該次結果標為探索，另收集新保留集驗收。保留完整的執行版本、prompt/policy 版本、模型與日期，不能只挑成功結果。

語料沒有附真實錄音，不能據此量測語音辨識本身準確率。它測的是文字已輸入後的校對能力。接續真人試用要增加匿名化且經本人同意的例句，但不可擅自把私人草稿提交到 GitHub。

## 指標定義

### 1. 明確錯句修復率（目標 ≥ 80%）

在 `kind=error` 的集合中，將模型候選的首選局部修正套用後，**完整結果精確等於 `expected`** 的句數 ÷ 明確錯句總數。保留原文、部分修復、錯修或超額改寫均不算修復成功。供應商逾時、格式錯誤、拒絕等也算該次未修復，不得從分母刪除。

這個指標可以評估「候選能不能修對」，並不代表那些修改已獲准自動套用。另列每一類的樣本數、成功數及失敗原因。

### 2. 自動修改正確率（目標 ≥ 99%）

以**局部修改為單位**：符合 gold 最小修正範圍與文字、且沒有額外改動的自動修改數 ÷ 全部自動修改數。正確／歧義句上的任何自動修改算錯；錯句中的過度潤飾也算錯。

沒有自動修改時，值為「N/A（樣本不足）」而不是 100%。工具先尋找唯一的最小 Unicode 編輯對齊，再以局部修改計算 `autoPrecision`。若重複字等情況導致對齊不唯一，列為 `unscoredAutoEdits`，`autoPrecision` 回傳 `null`，不支援 99% 門檻；另提供把未評分算錯的保守下界。`sentenceAutoPrecision` 是整句參考值，不能取代局部修改門檻。

目前產品 policy 沒開自動修改；評估工具所用政策明示為 `hypotheticalPolicyOnly`，真實自動修改精確率不可被候選結果冒充。可在離線驗收中比較「擬啟用政策」的反事實結果，不可說它已在產品中通過。

### 3. 誤報率

對 `correct` 和 `ambiguous` 分別計算：至少出現一個不需要的建議的句數 ÷ 該類總句數，稱為**建議誤報率**。另計至少有一個錯誤自動修改的句數 ÷ 該類總句數，稱為**自動誤改率**。不要把兩者合成單一數字掩蓋實際使用干擾。

### 4. 延遲（端到端 P95 目標 ≤ 2,000 ms）

起點為使用者**最後一次有效輸入／組字結束**，終點為對應版本的校對結果在畫面可見。必須包含約 600 ms 停頓、背景傳遞、網路、模型及畫面更新。API-only 延遲只作診斷，不能當作端到端數字。

有效樣本排序後，P95 使用第 `ceil(0.95 × N)` 個值。分開記錄冷啟動、一般輸入與六人併發；同時列出樣本數、超時率及失敗率。逾時／失敗不能靜默排除：它們沒有成功回應，記為失敗並阻止用成功樣本 P95 宣稱全部請求達標。

CLI 欄位 `estimatedSuccessfulApiPlus600msP95` 只是在成功 API 時間上加固定 600 ms 的估算，排除失敗，沒有包含瀏覽器訊息與畫面更新，**不是端到端 P95**。工具的 `realEndToEndP95Ms` 保持 `null`、`realEndToEndLatencyGatePassed` 保持 `false`；須另做真實瀏覽器測量。

### 5. 真人使用指標

用匿名填表觀察每次人工修改所需時間、錯誤候選／自動修改的還原次數、使用天數與是否願意繼續。這些數據不由 BYOK 背景遙測蒐集。至少五位外部測試者中三位使用四天以上並願意保留，才通過保留意願門檻；表格在 [PILOT.md](PILOT.md)。

## 執行方式與預算

開發測試與託管試用共用 NT$300 總預算：模型比較 NT$60、試用 NT$210、匯差／計費緩衝 NT$30。模型比較再分配為**本機評測 NT$55＋託管驗收 NT$5**，不能各自在兩套帳本使用完整 NT$60。託管驗收和試用合計上限 NT$215，本機上限 NT$55，合計 NT$270，保留 NT$30 緩衝。

由我們執行的 BYOK 付費測試也包含在本機 NT$55 內。真人瀏覽器 BYOK 驗收之前，必須在同一私有本機帳本預留可覆蓋該次驗收的費用，再記錄結算；目前 CLI 的預留只涵蓋自己的請求，**不能直接在 BYOK UI 點測試或打字，然後假設 CLI 已替它記帳**。尚未接好受控預留流程時僅可執行 mock 瀏覽器驗收。外部使用者自己的 API 費用不在此專案預算內。

不能借用另一支金鑰繞過專案上限，或把失敗請求當作免費而不記錄。

模型驗證工具讀取**目前程序**的 `GEMINI_API_KEY`，不得把金鑰寫進 README、Git、報表或命令列範例。先由本機安全環境提供可用憑證，再執行：

```sh
npm run eval -- --split dev --limit 5 --run-label smoke-v0_1_0
npm run eval -- --split dev --run-label dev-v0_1_0
```

凍結模型、prompt、校對規則與擬啟用政策之後才執行：

```sh
npm run eval -- --split holdout --run-label holdout-v0_1_0
```

缺少金鑰時工具拒絕付費評測；`--limit` 僅供小批檢查，不可用部分子集冒充完整驗收。報告記錄 `planned`、`attempted`、`unattempted`、`completionStatus`、完整集合大小與停止原因。權限／模型不可用等永久錯誤立即停止；連續兩次相同網路、逾時、限流或其他失敗也會停止後續付費請求。提前停止會留下 `partial`／`not-started`，不能視為完整 holdout。

每次呼叫前預留保守最大費用，以 `.local/eval-budget.sqlite` 管理本機 NT$55 額度。實際使用估算超出單次預留時，工具會記帳實際費用、停止後續請求並寫入永久 guard；重新啟動也不能繼續。非有限或負數成本同樣觸發 guard。不要刪帳本或換 run label 繞過；須由維護者稽核費率、預留上限、帳單與剩餘預算，另行處理恢復。供應商價格變動時先更新成本估算，不能在不知道成本時繼續跑完語料。

本機原始報表放在 `.local`，不提交憑證或可識別使用者的內容。需要公開時，只提交去識別統計到 `docs/evaluation-report.json`，包含版本、模型、日期、樣本數、各項指標、估算費用、失敗數與限制。不得宣稱尚未執行的測試已通過。

## Gemini 與 Jev 比較

基準是 `gemini-3.5-flash-lite`。先在 dev 建立可用基準，再以相同輸入、相同 Gemini 候選及明確固定的政策，比較是否由 Jev 選擇／拒絕候選。Jev 不是改字生成器；必須把原文也當作可保留的選擇。

除了正確率，也比較誤改、額外費用、失敗率和**總端到端**延遲。只有在未受污染的驗收資料上改善誤改表現，且仍符合速度與預算，才列入產品。預設 BYOK 仍只需要一把 Gemini 金鑰；沒有證據就不加 Jev 呼叫。API 無法使用或預算不足時，記錄未完成，不捏造比較結果。

## 另外必須通過的工程驗收

- 核心：重疊／越界／非原文修改、數字、名稱、程式碼、網址與引用錯字的防誤改；草稿不能覆寫系統指令。
- 輸入框：組字期間、繼續打字、移動游標、復原、切換對話、送出與舊回應相遇時，不遺失或替換錯誤版本的文字。
- 憑證：BYOK 無順字伺服器請求，網站無法讀取金鑰；儲存、重啟、背景程序休眠、更新、清除與拒絕來源正確。
- 可靠性：斷線、超時、401／403、429、模型回應格式錯誤、草稿超長及沒有金鑰，都不妨礙正常輸入。
- 託管：六人併發時的預算預留、限流和版本回應正確，既有網站健康狀態不退化。
- 發布：原始碼與 ZIP 無憑證、私有伺服器秘密或使用者私人資料；至少一位真人僅依 README 完成安裝與首次校對。

工程 mock 測試與真實模型驗收分開報告。任何要求未完成，狀態應保持待驗證，不能用「完成程式」取代「完成發布」。
